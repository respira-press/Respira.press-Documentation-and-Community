## Respira CLI Releases

<Update label="2026-04-19" description="Respira CLI for WordPress v0.1.0: initial release" tags={["feature", "cli", "sdk", "ai-agents"]}>

### What's New in Respira CLI v0.1.0

The modern WordPress command line for developers working with AI coding agents.

**Three npm packages**
- `@respira/cli`: the oclif-based CLI with 29 commands across auth, sites, read, write, find-element, tools, docs, snapshots, exec, init-claude-code
- `@respira/sdk`: the typed TypeScript client with zod validation on every method
- `@respira/cli-core`: shared auth store (OS keychain with file fallback), output formatter, and API client with retry plus rate-limit handling

**Anonymous mode**
- `respira read structure <url>` works on any public WordPress site with no account
- `respira read design-system <url>` returns colors, fonts, and spacing from any public site

**Builder-native**
- Elementor, Divi (4 and 5), Bricks, WPBakery, Beaver Builder, Oxygen, Breakdance, Brizy, Thrive Architect, Flatsome UX Builder, native Gutenberg blocks, plus WooCommerce

**Safety-first**
- Every write creates a snapshot first
- `--dry-run` on every write command
- `--diff` on `write edit-page` and `write edit-element` emits before/after for agent review
- Destructive operations require `--confirm`

**AI agent integrations**
- `respira init-claude-code` sets up Claude Code in the current directory with a skill + shortcut commands
- JSON output when piped, so every agent framework can consume results

**Installation**
```bash
npm install -g @respira/cli
respira auth login
respira sites list
```

Documentation: [respira.press/cli/docs](https://www.respira.press/cli/docs). Source: [github.com/respira-press/respira-wordpress-cli](https://github.com/respira-press/respira-wordpress-cli).

Not a WP-CLI replacement. WP-CLI is excellent for server-side WordPress administration and the two tools are complementary.

</Update>

## WordPress Plugin Releases

<Update label="2026-10-02" description="Respira for WordPress v9.1.13 + MCP Server 8.4.11: reading an option no longer hands another plugin's keys to the AI" tags={["release", "security", "options", "safety"]}>

### What's New in v9.1.13

**Keys stay on the site**
- `wordpress_get_option` shows keys, tokens and passwords as `[redacted]`, the way a listing has since 9.1.0, and names the hidden fields in `redacted_fields`. Everything else in the option reads as before.
- `reveal_secrets: true` returns the full value after a person approves it. An option with nothing to hide never asks. See [wordpress_get_option](/tools/options/get-option).
- `wordpress_update_option` refuses a value that carries the placeholder, with `respira_redacted_value_in_write`, so a real key cannot be overwritten with the text "[redacted]". See [wordpress_update_option](/tools/options/update-option).

**Also in this release**
- The rules every AI app receives now say who builds Respira and who answers support.
- A connection whose profile switches `get_option` off is now refused over REST too.

</Update>

<Update label="2026-10-02" description="Respira for WordPress v9.1.12: Respira can update itself, one switch per site and one for every site" tags={["release", "updates", "dashboard"]}>

### What's New in v9.1.12

**Automatic updates for Respira**
- One switch under Respira > Settings > Safety controls, in the Updates card. It is off until you turn it on, and it is the same switch as WordPress's own Enable auto-updates link on the Plugins screen.
- It updates Respira only, on WordPress's own schedule, twice a day. A new major version always waits for you, and an update waits while a Respira job is running.
- Afterwards Respira's screens say which version it moved to, or why it could not, and both land in the activity log. On WordPress 6.6 and later, WordPress puts the previous version back if an update causes a fatal error.
- Where the server stops WordPress's updater, the switch stays off and says what stops it.

**The same switch on the dashboard**
- The [Sites page](https://www.respira.press/dashboard/sites) shows the switch on each site, and one action for every site at once.
- Agents cannot change it. It is not a tool, and the options behind it are protected.

Full page: [Automatic Updates](/automatic-updates). No MCP server release is needed.

</Update>

<Update label="2026-10-02" description="Respira for WordPress v9.1.11 + MCP Server 8.4.10: find_in_page, JSON-LD blocks with their values, find_element by content on every builder" tags={["release", "analysis", "seo", "builders", "bugfix"]}>

### What's New in v9.1.11

**find_in_page: text that is not in the page content**
- `respira_find_in_page` is a new read tool for schema, tracking tags, verification tags and anything pasted into a header or footer code setting. Give it a post ID or an address on the site and the text. It reads the published HTML, head included, and returns each match with the tag around it and 200 characters either side, or every JSON-LD block with `kind: "jsonld"`.
- `sources` checks the places head code lives on the site (Elementor Custom Code, WPCode snippets, the WPCode header and footer options, Perfmatters, the Divi, Avada and Bricks code settings, GeneratePress hook elements, the theme's Customizer code settings) and says which one holds the text, with its id or option name, a short context and the length, never the whole body.
- Options Respira protects are skipped, addresses on other sites are refused, and a redirect is followed only while it stays on the site.
- Tool page: [respira_find_in_page](/tools/analysis/find-in-page).

**check_structured_data shows the values**
- `blocks` lists every JSON-LD block on the published page: head or body, every `@type`, size, the plugin that printed it (`emitter`), whether it is valid JSON, and the decoded JSON up to 4,000 characters.
- `contains` keeps the blocks that hold a value, each with 200 characters of context, and `where_to_edit` says where each one is changed.
- The tool reads the published page on every call. See [wordpress_check_structured_data](/tools/analysis/check-structured-data).

**Fixes**
- `find_element` by content, text or class works on every builder Respira reads. Each match names its field with a snippet, at most 20 with `truncated`. A search that finds nothing is a normal answer with `found: 0` and where to look next, where it used to answer HTTP 404. A class search on Elementor now reads the custom class setting. See [respira_find_element](/tools/builders/find-element).
- A published page that dies while rendering is no longer read as empty. When PHP printed a fatal error with HTTP 200, the analyzers searched the error text; the page now counts as unreadable, with the reason.

</Update>

<Update label="2026-10-01" description="Respira for WordPress v9.1.10 + MCP Server 8.4.9: the security scan finds what wp-admin does not show, quarantine for a plugin that should not be there" tags={["release", "security", "plugins", "safety"]}>

### What's New in v9.1.10

**The security scan reads what the admin screens do not show**
- A plugin that is active and filtered out of the plugin list is reported as `hidden-active-plugin`, and an active file with no plugin header as `active-file-without-plugin-header`.
- A rewrite rule that answers the site's page addresses before WordPress's own page rule is reported as `rewrite-rule-shadows-pages`, with the pages it takes over.
- The scan also names which plugin, theme or loose file serves each REST namespace, where each plugin comes from, and any stored list of search-engine crawler addresses.
- Page: [Security scan](/security/security-scan).

**Quarantine, restore, rebuild**
- `wordpress_quarantine_plugin` stops a plugin without running any of its code and keeps every file, with a manifest. It also reaches an active file with no header and a must-use plugin file. See [wordpress_quarantine_plugin](/tools/plugins/quarantine-plugin).
- `wordpress_restore_quarantined_plugin` moves it back, inactive. See [wordpress_restore_quarantined_plugin](/tools/plugins/restore-quarantined-plugin).
- `wordpress_flush_rewrites` rebuilds the rewrite rules from what is installed now and lists the rules that went. See [wordpress_flush_rewrites](/tools/other/flush-rewrites).

**Owner approval, opt-in**
- With `RESPIRA_OWNER_APPROVAL` on, installing, deleting, quarantining or restoring a plugin, deleting a user and deleting an option wait for an administrator to press Approve in wp-admin. See [Owner approval](/security/owner-approval).

**Fixes**
- Deleting an option that does not exist answers `already_absent: true` instead of an error.
- Plugin install, activate, deactivate, update, delete, quarantine and restore are written to the activity log, and so is a refused write to a protected option. Activity rows for options carry the option name.

</Update>

<Update label="2026-09-27" description="Respira for WordPress v9.1.0 + MCP Server 8.4.0: plan mode, the guarded plugin update, cards in Respira AER, site skills" tags={["release", "plan-mode", "security", "skills", "safety"]}>

### What's New in v9.1.0

**Plan mode for every MCP client**
- `respira_begin_session` with `mode: "plan"` makes every write answer a `respira_plan_step` instead of changing the site: the tool, its arguments with secrets hidden, the predicted effect, and whether it would land on a draft copy or the live item. Reads run as usual.
- `respira_apply_plan` runs the steps in order, each through the same checks as a direct call, and returns one receipt with snapshot ids and preview links. The apply call is the person's approval for a step whose tool asks for one, and the receipt names those steps.
- `respira_get_plan` shows the plan, `respira_discard_plan` empties it, and `respira_end_session` turns plan mode off and says how many steps never ran. One write can be planned without a session by sending `_respira_plan: true`.
- Guide: [Plan mode for MCP clients](/guides/plan-mode-for-mcp-clients).

**Guarded plugin update**
- `guarded_plugin_update` updates one wordpress.org plugin to the exact version offered, with a restore point before and four health checks after, and puts the previous version back from wordpress.org when a check fails. Duplicator and BackWPup take a fresh backup through their abilities and the run waits for it; UpdraftPlus is started and watched; any other provider, or none, closes the one-click path unless the caller says that no restore point is accepted.
- `take_backup` is the restore point step on its own. `check_guarded_update` is the same preflight as a read. `get_guarded_update` reads a run's progress and its receipt.
- The REST route takes `_respira_async` and refuses to run inside the request unless asked.
- Guide: [Guarded plugin update](/security/guarded-plugin-update). Cards: [Cards in Respira AER](/dashboard/aer-cards).

**Site skills**
- Respira > AI Skills holds short Markdown pages that tell every agent how a thing is done on this site, each with an on/off switch and an "agents may edit" switch. Every save is a revision. `respira_list_skills`, `respira_get_skill`, `respira_write_skill` and `respira_delete_skill` read and write them; the enabled skills ride in `respira_get_site_context` under `site_skills`.
- A new screen, What your AI is told, shows in order what an agent receives from this site.
- Guide: [Site skills](/site-skills).

**Connecting**
- A host that strips the Authorization header no longer ends the connection: Respira's clients send the credential a second time in `X-Respira-Authorization`, and the plugin uses that copy when a request arrives with no credential at all.
- Respira > Troubleshoot runs the connection checks from the site's own server, shows each as pass or fail with one next step, and produces a plain-text report for a hosting support team.
- Setup's "connect your agent" step has a prompt to paste into an agent so it connects itself.
- Errors on the connection, sign-in and approval paths carry `cause` and `retry_ok`.

**Divi 5: native attributes by default**
- Every agent write to a Divi 5 page takes `allow_inline_styles` and `allow_code_modules`, both false by default. A style with no native place comes back in the write result as `unmapped_styles`; a write that adds a `divi/code` module is refused with the native module to use. See [Divi 5 Support](/builders/divi-5).

**Block editor writes are render-checked**
- After a write to a block editor page, Respira parses and renders the saved markup and reports `render_validator_pass`, `validator_warnings` and the `snapshot_uuid` that undoes the write. See [Gutenberg](/builders/gutenberg).

**Abilities from other plugins**
- `search_abilities` searches every ability registered on the site at the moment of the call and says for each whether Respira can invoke it now and, when it cannot, why not.
- Respira > Abilities has a new setting, off unless the site owner turns it on: "Let Respira run read-only abilities".

**Safety**
- A delete through Respira can be undone: pages, posts, custom posts and media go to the trash with a snapshot first, and the answer carries `snapshot_uuid`.
- An agent can no longer change the options that lock people out of a site (`siteurl`, `home`, `active_plugins`, the roles option, every key and salt, Respira's own settings and more): refused with `respira_option_protected`.
- Every SVG uploaded through Respira is cleaned first; one that cannot be made safe is refused with `respira_svg_unsafe`.
- A theme file write stores the file's current bytes in a snapshot first.
- The audit log keeps entries for 180 days by default, set under Respira > Settings > Audit & approvals.
- Tool switches and profiles now bind on the site's own MCP endpoint too, not only over REST and the npm server.
- Background writes sent with `_respira_async` start right away, and every job record is signed.
- `update_comment` takes `status` as `approve`, `hold`, `spam` or `trash`.

Full details in the [GitHub release notes](https://github.com/webmyc/respira-wordpress/releases/tag/v9.1.0).

</Update>

### What's New in v8.0.0 "Canopy"

Respira has always been strong on page builders and thin on the thing WordPress core is actually pushing people toward. 8.0 closes that. The coverage line is now **16 page builders plus the native Site Editor**.

Measured on a live install: **197 tools** on any WordPress site, **302** with the WooCommerce add-on (of which **105** are `woocommerce_*` tools), **269** WebMCP abilities, **37** skills.

**The native WordPress Site Editor is a first-class target**
- Block templates and template parts (`wp_template`, `wp_template_part`) with template hierarchy and source discovery, so you know whether a template is theme-provided, plugin-provided, or a database customisation
- Synced and unsynced patterns (`wp_block`). Registered theme and plugin patterns stay read-only. Editable user patterns support the synced/unsynced distinction
- Block navigation (`wp_navigation`) edited by exact block path, not by rewriting the navigation document. A guessed path is refused. A stale revision is refused
- Gutenberg design tokens and global styles

**The safety contract for structural writes**
- Every structural write is fingerprint-guarded against a stale base, snapshotted, read back through WordPress, and server-render verified. It returns `verified` only after WordPress actually rendered it
- Structural proposals: a write can be staged for human approval instead of applied
- The mutation-result contract is explicit: `dry_run`, `pending_approval`, `verified`, `stored_unverified`, `no_match`, or a failure with a reason
- An agent-facing activity history links audit entries to snapshots, proposals, approvals, and rollbacks

**Structural writes are beta-gated**
- Structural writes to site-level objects are beta-gated per site and OFF by default. Read-only discovery works everywhere. The gate stays until that write path has more live mileage

**Two safety fixes found by auditing the safety layer itself**
- A Divi 4 serializer rule written for brand-new pages was firing on every write path, retyping existing Code modules on pages it should only have passed through
- Undoing a Theme Builder create could trash a template the agent never created

**Divi Theme Builder: a confirmation handshake, not an approval**
- Divi Theme Builder global layouts are snapshotted and reversible but written live, not staged. They cannot be staged the way a page can, because Divi resolves a global layout by id and a duplicate would compete with the original
- The first attempt to rewrite a global header, footer, or body is now refused with `respira_tb_live_edit_confirmation_required`, naming the layout and saying it changes every page using it. Re-send with `confirm_live_edit=true` to proceed
- That is a confirmation, not an approval. A confirmed write goes live

**Credit**
- The FSE work was driven by a published field study from Dale Smith of [revWorx](https://revworx.ai/), who builds exclusively on FSE block themes and documented, live-verified, that Respira's storefront tools went inert on that stack

Documentation: [Site Editor (Full Site Editing)](/builders/site-editor).

## Installation Instructions

### WordPress Plugin

1. Download the latest plugin ZIP from the links above
2. Go to **WordPress Admin → Plugins → Add New → Upload Plugin**
3. Upload the ZIP file and click **Install Now**
4. Activate the plugin
5. Go to **Respira → API Keys** to generate your API key

### MCP Server

The easiest way is the setup wizard:

```bash
npx @respira/wordpress-mcp-server --setup
```

Or install globally:

```bash
npm install -g @respira/wordpress-mcp-server
```

For detailed setup, see the [Installation guide](/installation).
