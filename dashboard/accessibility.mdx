## WCAG Scanner

The [WCAG Scanner](https://www.respira.press/dashboard/accessibility) in your Respira dashboard checks any public page for accessibility problems. Paste a URL, wait for the report, and get a score, the list of failures and a fix prompt for each one. It is in public beta, and it is included with every paid plan: 10 scans a month, no separate purchase and no add-on. A free plan sees an upgrade card instead of the scanner.

You need to be signed in. There is no anonymous scan.

## What it does

When you press **Run scan**, Respira asks Google PageSpeed Insights to load the page. PageSpeed runs a Lighthouse accessibility audit, and those audits use axe-core rules. Respira turns the result into a report. The scan usually takes 30 to 60 seconds.

For each failure the report shows:

- **Severity**: critical, serious, moderate or minor
- **The rule** that failed, and the WCAG success criterion it belongs to
- **The affected element**, with a selector and a snippet of its HTML
- **A fix prompt** you can paste into Claude, Cursor or Codex. On a WordPress site the prompt is written for the page's builder.

The scanner sees what any visitor sees: the public HTML, CSS and accessibility tree. It cannot see logged-in pages, private pages, localhost, an intranet, or a page that blocks Google PageSpeed. It does not need the Respira plugin on the site, and it does not touch the site.

## What a scan does not tell you

WCAG 2.2 has 86 success criteria. Lighthouse checks the part of the Level A and AA rules that a machine can test automatically. That is a subset of WCAG, and some criteria cannot be tested by a machine at all. A clean report does not mean the page is accessible, and it does not mean it is legally compliant with the ADA, WCAG, the European Accessibility Act or any other rule. It is information, not legal advice.

A scan cannot judge:

- **Keyboard use** of complex widgets, which needs a person.
- **Screen reader order and wording**, which needs a real screen reader.
- **Motion and animation** for people who ask for less motion.
- **How clear the language and the task flow are.**

Use the scan to catch the mechanical problems: missing alt text, low contrast, heading order, form labels, ARIA. Then test the rest by hand.

## Running a scan

1. Open [dashboard/accessibility](https://www.respira.press/dashboard/accessibility).
2. Paste a public URL.
3. Press **Run scan**.
4. Read the score and the failures. Open **Fix prompts** on any report to copy the prompt for a failure.

## Sharing reports

Every scan gets a public report link. Press **Copy link** on a row of your scan history and send it to a client or a colleague. Anyone with the link can read the report without a Respira account. The report is read only.

## Limits

| What | Limit |
| --- | --- |

When you have used your 10 scans, the dashboard says so and the next scan waits for the 1st. The limit applies to each signed-in person.

## Scanning from an AI agent

Separate from the dashboard scanner, the Respira plugin has MCP tools that scan a page of a connected site, so an agent can scan, review and fix accessibility issues in one conversation. Four tools cover the flow. They run on your site through the plugin, not through Google PageSpeed Insights, and they do not use the 10 scans a month of the dashboard scanner.

### respira_scan_page_accessibility

Run a WCAG scan on a page. The scanner runs an axe sweep against the page's public URL: `page_id` is resolved to the permalink server-side before the scan. The result groups violations by severity (critical, serious, moderate, minor) with auto-fix suggestions.

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| page_id | number | Yes | Page ID to scan. Resolved to the page's public permalink before scanning. |
| standard | string | No | WCAG standard to test against (default `wcag2aa`). Supported: `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`, `section508`. |
| url | string | No | Explicit URL override. When set, skips the page_id lookup. Use it for staging or preview URLs that do not map to a Respira page_id. |

### respira_list_accessibility_scans

List previous scans with scores and violation counts. It defaults to `summary_only=true`, which strips the per-node detail and the AI fix prompts from each entry. Those add up to roughly 30KB per scan and blow past the MCP response cap once you have five or more scans, so keep `summary_only` on for browsing and only set it to `false` when you genuinely need the full payload.

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| limit | number | No | Max scans to return (default 20). |
| offset | number | No | Pagination offset (default 0). |
| summary_only | boolean | No | When true (default), omits `violations[].nodes` and `prompts[]`. |

### respira_get_accessibility_scan

Get the full detail of one scan: every violation, the scores, and the AI fix prompts. Pass the `scan_id`, which is the UUID string from a `list_accessibility_scans` entry's `id` field. This is where you get the full payload that `list_accessibility_scans` leaves out in summary mode.

### respira_apply_accessibility_fixes

Auto-apply fixes for a scan. Pass the `scan_id`, and optionally a list of `rule_ids` to fix a subset; omit `rule_ids` to fix everything that is auto-fixable. The fixes it can apply are: `image-alt`, `color-contrast`, `label`, `heading-order`, `document-title`, and `html-lang-valid`.

### A typical agent flow

```text
1. respira_scan_page_accessibility on page 42
2. respira_get_accessibility_scan for the full violation detail
3. respira_apply_accessibility_fixes for the auto-fixable rules
4. respira_scan_page_accessibility again to confirm the score improved
```

Anything the auto-fixer cannot handle stays in the report for manual work, the same way the dashboard scanner leaves keyboard and screen-reader issues to human testing.

## Privacy

A scan stores the address you scanned, the page title, the score, the failures it found with the HTML snippet of each affected element, and your account. Reports expire after 90 days.
