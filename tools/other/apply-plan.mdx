# respira_apply_plan

Run the planned steps on the site, in plan order, each through the same checks it would meet as a direct call, and return one receipt with each step's outcome, snapshot ids and preview links.

Call it only after the person has read the plan and said yes: this call is their approval, including for steps whose tool asks for approval, and the receipt lists those steps. It stops at the first failed step unless `continue_on_error` is true; steps that did not run stay in the plan.

## Parameters

2 parameters, none required.

| Name | Type | Required | What it is |
|---|---|---|---|
| `step_ids` | array of string | no | Steps to run. Leave out to run every step that is waiting, in plan order. |
| `continue_on_error` | boolean | no | Keep running later steps after one fails. Default false. |

## Example call

```json
{
  "name": "respira_apply_plan",
  "arguments": {}
}
```

## Response

      "position": 1,

A step's `outcome` is `applied`, `failed` (with `error.code`, `error.message` and `error.status`) or `not_run` (an earlier step failed and `continue_on_error` was not set; the step is still in the plan).

## What it changes

It runs the writes the plan holds, so treat it as the careful kind of call. Each step replays the request it stored through the same door it arrived by and the same gates a direct call meets: site governance, key scope, permission, the duplicate-first rule. Respira takes a snapshot for each step and the receipt carries the ids, so any one step can be undone with `respira_restore_snapshot`. A step whose tool asks for a person's approval runs without a separate token, because this call is that approval; the receipt names those steps under `approved_by_apply`. On a connection set to read-only nothing was ever planned, so there is nothing to apply.

## When it fails

- `respira_plan_step_not_pending`: a named step is not waiting (already applied, failed, or discarded). Call `respira_get_plan` for the current ids.
- `respira_plan_step_unknown`: a named step id is not in this key's plan.
- `respira_plan_needs_key`: the connection has no Respira key of its own, so it has no plan.

## Availability

Plugin 9.1.0 and MCP server 8.4.0. On the site's own MCP endpoint the tool is `respira_wordpress_apply_plan`.

## Notes

- Never call this on your own. A `respira_plan_step` is a question for the person; apply only after they say yes
- Applying does not end plan mode; the next write is planned again until `respira_end_session`
